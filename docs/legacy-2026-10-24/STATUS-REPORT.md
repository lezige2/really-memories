## 1. 架构现状（我们在哪）

### 1.1 已彻底封版 —— C++ 引擎层

这一层是**物理定律层**，下面所有东西都建立在它之上。它已经编译通过、跑通、并且有强不变量保护，
**除非要改动 K 的存储格式，否则不应该再碰**。

| 能力 | 状态 | 说明 |
|---|---|---|
| 单块记忆的独立生命周期 | ✅ 封版 | 每块一个 `seq_id`，`seq_rm` 释放，`state_seq_save/load_file` 落盘 |
| 局部 RoPE 重旋转 `seq_repos_local` | ✅ 封版 | 只碰"真正移动"的 cell；按连续区段批量搬；**同步完成，不留 pending shift** |
| Hadamard 基下的正确 rope | ✅ 封版 | `H → rope → H`，与 `build_graph_shift` 同构 |
| 跨序列可见性（多块拼接） | ✅ 封版 | **不需要拼 mask**：`seq_cp` 是引用计数，mask 闸门只有 `seq_has(cell, seq_id)` 一行 |
| 多块同时可见 | ✅ 跑通 | 2 块（86 cell）同时挂载，答案能区分归属 |
| 零污染保证 | ✅ 有验证 | 未移动序列 **0 B / 100 次移动** 逐字节相同 |

**这一层的本质**：位置（position）是一等公民。块的 K 里编码着"我是在第几个位置生成的"，
所以移动一个块 = 把它的 K 旋转到新位置。因为 RoPE 的角度对位置是**线性**的
（`theta_j = pos · w_j`，连 yarn 的 ramp 都只依赖维度下标），所以"旋转 Δ"在数学上就等价于"位置平移 Δ"，
一次矩阵旋转即可，不需要重放 token。

它不是"参考材料"，它是**经历过的上下文**。

## 3. 踩坑与硬约束（绝对不能再碰的红线）

下面每一条都有**判据**（怎么在 5 分钟内发现自己违反了它），不是经验之谈。

### 3.1 物理定律

#### L1. K 存在 Walsh–Hadamard 基里 —— 直接做 rope 一定错

本 fork 对量化 K 默认开 attention rotation（`llama-kv-cache.cpp:325-352`：`model.attn_rot` &&
量化 `type_k` && `head % 64 == 0`）。本模型三条全中 → **`n_rot_k = 128`**。
写 K 时乘了正交 Hadamard 矩阵 H（Q 也乘，故内积不变），而 **RoPE 与 H 不对易**，
所以正确姿势是 `H → rope → H`（`build_graph_shift` 就是这么做的）。

- 表现：块位置对、mask 也看得到，但答案是**纯复读**（"我的工号是多少？ 答：我的工号是多少？"）。
- 判据：`LLAMA_ATTN_ROT_DISABLE=1` 时**旧块文件直接加载失败**（状态文件存了 `n_rot_k`，
  `llama-kv-cache.cpp:2782` 校验不匹配）。加载失败 = 这棵树的块是在 H 基下保存的。
- 实现：`llama_kv_fwht()`（正交 Sylvester，`res² = I`，O(n log n)）。

#### L2. `pos_add` 会置 `has_shift` —— 手动旋转过就必须用 `pos_move`

`cells.pos_add()` 干两件事：改 `pos[]`，以及 `shift[i] += d; has_shift = true`。
后者会让下一次 decode 再跑一遍 `build_graph_shift` → **同一个块被旋转两次**。

- 表现：答案偶发崩坏、难复现（因为取决于下一次 decode 发生在什么时候）。
- 正解：`pos_move()`（本轮新增）。`pos_set()` 不能用 —— 它 `assert(pos[i] == -1)`，只允许写空 cell。

#### L3. 零字节隔离是硬指标，不是"应该不会"

同一池里别的序列，在任意次移动后必须**逐字节不变**。

```
N=100     chat=236 tok | 3/3 correct
hold state: 1463748 B, 0 differing after 100 shifts (0.00%)
```

- 判据：`kvdrift.py --reload --local` 看 `hold state` 那一行，必须是 `0 differing`。
- 为什么能做到：新路径**物理上**只读写了那几百个 cell 的字节，没有"重写整张张量"这一步。

**这条的适用范围必须写清楚（2026-10-24 更正）**：它证明的是
「**placement 不会碰没参与的序列**」，因为 `kvdrift.py` 每次都从磁盘重新加载 pristine 块，
且 hold 序列从不被移动。它**不**证明「同一块反复移动不会退化」——见 L3b。

#### L3b. 移动不是免费的：一块大约只能承受 ~10 次往返

q8_0 的 K 在每次移动时都要 dequantize → 旋转 → quantize，是**有损**的。
实测（`kv_audit.py drift`，同一块反复 `+64/-64` 往返后回到原位，再提问）：

| 往返次数 | 实际移动次数 | 答案 |
|---|---|---|
| 0 | 0 | 我的工号是 A-4417。 ✓ |
| 1 | 2 | A-4417 ✓ |
| 5 | 10 | A-4417 ✓ |
| 10 | 20 | A-4417 ✓ |
| **25** | 50 | **A-444417**（数值已坏）|
| 50 | 100 | `ioneerioneer`（崩）|
| 100 | 200 | `3`（崩）|

- **判据**：`kv_audit.py drift --n 25` 若答案不再是 A-4417，就是越过预算了。
- **预算按 requantization 次数记，不按"移动次数"记**：`repos_local(+64)` 是一次 requantization，
  `+64` 再 `-64` 就是两次。上面的表里"25 次往返"= **50 次 requantization** 才崩。
- **保守上限：5 次往返 = 10 次 requantization**。表里 10 次往返（20 次）仍然答对，
  但那是**单块单问的 n=1 观察上界，不是安全线**——要扫多块多问才能定。
- ⚠️ 别用字节差异当漂移指标：状态文件里 1 次往返就有 6.8% 字节不同，因为
  q8_0 每 32 个元素存一个 f16 scale `d`，重量化让 `d` 抖 1 ULP 就会改写整组 int8。
  **数值漂移的可信指标是答案，不是字节数。**
- 推论（M3 必须做的三件事）：
  1. **pin 热块**：正被引用的块不许换出；
  2. **换出即从 pristine 文件重载**，绝不靠"再转回去"；
  3. 单块 mount 次数要计数，接近预算就从文件重载（不要指望无限次挂载）。
- 推论：`chat.py` 里 20 轮的 `+64/-64` 微基准**已经用掉该块 40 次 requantization**，
  所以它必须放在所有提问之后（现在就是这么排的）。

#### L4（已修订）. 致命的是「对话头上紧贴一个**看不见的**空位」，不是「任何洞」

旧措辞"位置必须首尾相连，洞 ≥ 1 就废"**是错的**，它把一次特定布局的观察当成了定律。
P0-4 的矩阵（`tools/hole_matrix.py`，5 位置 × {1,8,256} × 三种处置，问答各 1 次）给出：

| 洞的位置 | 空着 | 被别的 seq 占着但看不见 | 占着且 share 给对话 | 结论 |
|---|---|---|---|---|
| 全部块之下（底部） | ok ×3 | ok ×3 | ok ×3 | **无害** |
| 两块之间 | ok ×3 | ok ×3 | ok ×2 + 1 partial | **无害** |
| 块尾 → 对话头 | **全空** ×3 | **全空** ×3 | ok ×2 + 1 partial | **致命**，可修 |
| 对话内部（自己的 token 中间）| ok ×3 | ok ×3 | ok ×3 | **无害** |
| 对话尾部（下一用户的块在其上）| ok ×3 | ok ×3 | ok ×3 | **无害** |

机制（`tools/hole_probe.py` 直接量出来的，不是推测）：

1. 带洞时 `ask` 返回空串，且 `n_tokens` **仍是 0**——不是"生成了但没用上语料"，而是
   **一个 token 都没生成**；
2. `llama_decode` 返回非 0：`memory->init_batch` 走到 `FAILED_PREPARE`
   （`llama-context.cpp:1960`，只打 `WARN` 然后 `return 1`），我的 shim 在 `rc != 0` 时直接
   返回 -1，所以答案被吞成空串；
3. 同一个洞，只要把洞里的 cell **share 给对话自己的序列**（用例 D），立刻恢复正常
   （`A-4417`）；只差最后 1 个 cell 不可见（用例 E），又废。
   → 判据是「对话自己看得见的连续链」，不是「cell 是否存在」。

**为什么"对话内部"的洞不致命、贴着头的就致命**：结构上都是"pos_max 与解码位置之间缺一段"，
但前者的缺口在对话自己的 token 流里、后者紧贴解码位置。根因未完全定位（`init_batch` 内部
有分支依赖前驱 cell 是否可见），**但操作规则已经确定**，这才是设计要用的东西：

> **一轮对话的第一次解码，必须和对话自己可见的那条链首尾相接。**
> 洞放在这条链的**下面**无所谓；放在链**里面**也无所谓；只有夹在"链尾"和"新 token"之间才致命。

#### L4-D. 对固定 slot 的判决（P0-4 直接产出）

| 决策 | 结果 |
|---|---|
| 方案 B：chat anchor 固定、块向下紧贴 | ✅ **可行**。底部洞 1/8/256 全部正常作答，块把洞和对话隔开了 |
| 块尾与对话头之间出现洞 | ❌ 致命。**必须用 guard 填满并 share 给对话**（1/8 实测可救） |
| 方案 A（编码时 pad 到定长桶） | 不再必需，但仍是"布局完全不依赖洞"的稳定方案 |
| 对话内部/尾部有洞 | ✅ 无害 |
| 多用户拼在一条位置线上 | ✅ **有条件可行**：每个用户的 [块…对话头] 必须自己连续，洞只能落在**用户之间**；别的用户在洞下面（底部 other 臂）无害 |

一个附带结论：`chat_start = 块尾 + 1` 这条旧规则仍然有效，但它的理由不是"洞会破坏注意力"，
而是"解码前驱必须可见"。两者导出同样的布局，所以以前的实现不用改。

#### L4-E. 判决：采用 B-right（右对齐 slot），guard 退出常规路径

不用"左对齐 slot + 尾部留洞 + guard 填"，而是**每个块在 slot 内右对齐**：块尾贴 slot 尾，
顶槽的块尾贴 chat anchor。于是所有洞都落在块下面或块之间（矩阵已证无害），
**没有任何洞夹在链尾和新 token 之间，guard 根本不需要**。

`tools/p0_4b_right.py` 9/9（三块、四种问法、三条臂对照）：

| 臂 | 布局 | 解码 | 答案 |
|---|---|---|---|
| contiguous（基准） | 无 slot，块紧贴 | ✅ n=241 | 4/4 |
| **B-right（统一 slot 64）** | 尾部对齐，间隙 43/43/12 | ✅ n=239 | **4/4** |
| **B-right（间隙 14/28/44）** | 尾部对齐，按要求的间隙曲线 | ✅ n=241 | **4/4** |

左对齐那条是这组实验的**证伪能力**：如果它不失败，就说明这套测法根本分不出"贴住"和"没贴住"。

一次自我纠错值得记：第一版 B-right 只到 2/4，失败原因是模型拒答

样本量提醒：每组 1 个问题、1 次采样。表里 4 个 `partial` 都出现在 256 那档且不单调
（`between/guard`、`chat_head/guard`、`chat_inner/*`、`chat_tail/256` 的"上线"缺），
**按噪声对待**，不据此下结论；致命性那一列是"零输出"，不依赖采样。

#### L5. 块必须在对话**下方**，因为因果门是 `p0 > p1`

`llama-kv-cache.cpp:1686`：`if (p0 > p1) goto skip;`（cell 位置 vs 当前 token 位置）。
块的位置必须**严格小于**提问 token 的位置。

- 推论：块的顺序是有意义的（越晚的块越靠近对话），且**新块只能插在紧贴对话的位置**。

#### L6. `kv_unified=true` 下，同一 position 的写入会**复用 cell** 并互相覆盖

块文件都从 position 0 开始。若"先 load 两块、再一起平移"，第二块的写入会落在第一块占用的
cell 上 → 两块内容混在一起。

- 表现：答案把两块的信息串味（问工号答出项目日期），第一块"看起来"被第二块覆盖。
- 正解：**加载一块 → 立刻搬走 → 再加载下一块**（`chat.py` 现在的顺序）。

#### L7. `seq_cp` 是引用计数，不是拷贝

`llama-kv-cache.cpp:503-511` 同 stream 分支只做 `cells.seq_add(i, dst)`，**零字节拷贝**。

- 好处：挂载 86 cell 耗时 ≈ 0。
- 陷阱 1：源序列被 `reset` 后，如果还有别的 seq 引用这些 cell，cell 不会死（引用计数>0），
  但它的内容会随源序列的移动而移动。
- 陷阱 2（**移动对话时会踩**）：块被 `seq_cp` 给对话后，这些 cell **同时属于块和对话**。
  此时若对对话调 `repos_local`，会把块一起拖走。
  - 正解：先 `seq_rm(chat, 块区间)` 摘掉引用 → 移动对话 → 重新 `seq_cp`。

#### L8. 量化 K 不能走图写回（Vulkan 限制）

`ggml_get_rows` 只输出 F32；而 Vulkan 的 `supports_op`（`ggml-vulkan.cpp:9480`）只允许
`GET_ROWS / CPY / CONCAT` 带量化 src0，`SET_ROWS` 写 q8_0 不被支持。
→ **只能 CPU 逐 cell**，也正因此才拿到了 L3 的零污染。

#### L9. 纯旋转不能再乘 `mscale`

yarn 的 `mscale` 是**幅度**因子，编码时已经烘进 K 里。delta 旋转只该改角度。
多乘一次会让整块 K 的模长偏移，表现为"好像记得但说不准"。

#### L10. 8k 之外读不到 —— 是**当前配置下的经验曲线**，不是物理定律

> 2026-10-24 更正：原稿把这条写成"物理定律 / 记忆的物理上限"，过头了。数据本身有问题：
> **非单调**（0–1k 只有 56%，低于 2–4k 的 72%），而且 8–16k 只有 9 个样本、>16k 只有 3 个，
> 0/9 的 95% 置信区间约 [0%, 34%]，不足以支撑"绝对读不到"。也没有控制内容难度这个混淆变量。
> **它是"当前模型/当前 ctx 下的观察"，不是普适约束。** M2 的预算应据此设为软约束
> （按期望收益优化），而不是硬砍 4000 token。

实测召回率 vs 距离：

| 距离 | 召回 |
|---|---|
| 0–1k | 56% |
| 1–2k | 71% |
| 2–4k | 72% |
| 4–8k | 64% |
| 8–16k | **0/9** |
| >16k | **0/3** |

**常驻 ≠ 可读。** 这条决定了所有放置策略：挂着不动的块，距离超过 ~8k 就白挂。

#### L11. 成本模型

| 项 | 数值 |
|---|---|
| 每 token KV（q8_0） | 29.8 KiB（30,464 B） |
| 8192 ctx 的池 | **238 MiB** |
| 50 token 块落盘 | 1489 KiB |
| 移动 50 token 块 | **42 ms**（28 层 × 2 次传输，瓶颈是 submit+fence，不是带宽） |
| 移动 86 cell（两块） | 76 ms |
| 逐 cell vs 批量 | 508 ms → 115 ms → 42 ms（批量是必须的） |

移动耗时 ≈ `ceil(cells/256) × 28 × 2 × 0.75 ms`。**cell 数翻倍，耗时翻倍，与对话长度无关。**

#### L12. 内存与释放（**已实测**，2026-10-24）

- VRAM：`seq_rm(seq, 0, -1)` 把 cell 退回池（引用计数归零才真正空闲）；`kvshim_reset` 即此。
  8192 ctx 的 q8_0 池固定 238.0 MiB，**这块是常驻的，不随块数变化**。
- 磁盘：块文件是**唯一权威副本**，永不被原地修改（每次移动都不回写文件）。
- 主机 RSS：`kv_audit.py rss --cycles 50`（load → 移动 → 挂载 → 卸载 × 50，每 10 轮采样）
  实测 **4311.8 MiB 持平，全程 +0.22 MiB（一页）**，无单调上升。**没有泄漏。**
- 结论：**"磁盘不常驻"成立，"不占内存"不成立**——占的是一块固定的 VRAM 池（238 MiB），
  以及模型本身的主机 RSS（4.3 GiB）。旧文案里的"完全不占 16G 内存"是错的，已废弃。

### 3.2 红线（不可回退）

1. **不做 prompt 拼接。** 记忆文本永远不进 prompt；进 attention 的只有 K。
2. **索引只存指针，不存正文。** `chat.db` 里只有 `path / n_tokens / label`，没有正文。
3. **产物可删除而不影响产品。** 删掉 `blocks/*.kvmem` + `chat.db`，`chat.py build` 能重建；
   不依赖任何训练产物。
4. **ggml 不动。** 需要新算子时先问"能不能在 memory 层解决"。

### 4.0 现状与目标的差距（一张表）

| 模块 | 现在 | 目标 | 缺 |
|---|---|---|---|
| 记忆存储 | ✅ 块文件 + SQLite 指针 | 同 | — |
| 记忆挂载 | ✅ `repos_local` + `seq_cp` | N 块并发 | 规划器 |
| **记忆检索** | ⚠️ 索引已达标（= oracle），但 `chat.py` 仍写死两条 SQL | 接进产品路径 | M1 余项：**接入** |

**一句话：能"记住"，还不能"想起来"。** 现在是人肉告诉它该看哪两块。

### 4.1 M1 —— 海马体索引（**本轮已收口，结论：检索已饱和**）

#### 做完的事

| # | 动作 | 结果 |
|---|---|---|
| 1 | 修 `num` 正则（加 `\d{2,3}/\d{2,3}`）| Q13「血压」恢复命中 |
| 2 | `哪家` 从 `org` 移到 `place` | Q17 不再被错归 |
| 3 | 写了 `tools/facet_budget.py`：alpha 敏感性 + 块数预算实验 | 见下 |
| 4 | 发现并修掉背书闸门的**自毁 bug** | 见下（这是本轮最有价值的发现）|

#### 背书闸门原本是自毁的

设计意图：`max_score(S) >= alpha * max_score(global)` 才信 facet。但第一版实现写成了
`if best_all <= 0 or best_in < alpha*best_all: reject`。

**`best_all == 0` 时直接否决 facet —— 而"零词面重叠"正是 facet 唯一存在的理由。**
Q4 就是这种情况：文档通篇用「他」指代，问题里的「林知远」在全文**一次都不出现**
（`林知` 这个词 20 个块里 0 次命中），所以 BM25 对 Q4 返回**全零**，rank 5 只是
"按文档序平局"的假象。第一版闸门把唯一能救它的信号扔掉了。

修法：只在**存在词面证据且与之矛盾**时才否决——
`if best_all > 0 and best_in < alpha*best_all: reject`。

#### 实测（同一份 20 问 / 20 块 / q8_0，`n_predict=64`）

| 臂 | retrieval@1 | 端到端 | 说明 |
|---|---|---|---|
| oracle（金块） | 20/20 | **15/20 (75%)** | 上限 |
| **facet（strict）** | **20/20** | **15/20 (75%)** | **与 oracle 逐题 20/20 完全一致** |
| BM25 字 bigram | 19/20 | 14/20 (70%) | Q4 答成"行政部"（幻觉） |
| 错块对照 | — | 1/20 (5%) | 无记忆地板 |

**`facet == oracle`（不只是同分，是逐题答案完全相同）。** 检索这一侧已经打到天花板，
剩下 5 个错（Q6 猫→"薄荷"、Q7 书店复读、Q17 咖啡店复读、Q8/Q14 长尾跑题）**oracle 也全错**，
所以它们是**生成侧**的问题，不是检索侧的。

#### 三个诚实的限定

1. **alpha 在这份语料上测不出敏感性。** 金块对提问类型的覆盖率是 15/15 = 100%，
   意味着"facet 假设错误"这个事件从未发生，闸门没有机会拒绝任何东西，所以 alpha 从
   0.0 到 1.0 曲线全平。**闸门是保险，这份语料没有事故可保。** 要测 alpha 必须构造
   对抗集：问题问 `部门`，而金块里根本没有 org——那才是闸门该起作用的地方。
2. **+1/20 的绝对增益在噪声内。** 支撑 facet 的不是这个 +1，而是结构性论证：
   零词面重叠的查询对 BM25 **不可见**（返回全零），这是原理性的盲区，不是调参能解决的。
3. **本 QA 集测不了块数预算。** 每个问题恰好问一个事实，k>1 在构造上不可能涨点
   （recall 在 k=1..4 全是 95%/100% 一条平线）。k>1 的价值在于"一次问多个事实"，
   这份集里没有这种题。**不要读成"一个块就够产品用"。**

#### 结论与遗留

- **M1 在 k=1 上关闭**：facet 索引已经等于 oracle，继续调索引不会带来端到端收益。
  下一个 +1 必须从生成侧拿。
- `time` / `place` 两个 facet **今天零信息**（20/20 携带），而且抽取质量很差
  （抽出来的是 `下雨的那天楼`、`了一家面馆`、`他在办公室` 这类跨词边界的碎片）。
  它们现在因为"携带率 100% 被忽略"而无害，但在别的语料上可能偶然变成"有选择性"，
  反而危险。**建议：在需要之前直接删掉 time/place，只留 org/num。**
- 开着的两个实验：**对抗集测 alpha**、**多事实问题测块数预算**。两者都需要新语料，
  不是新代码。

> 历史数据（旧配置，不可与本表跨轮次直接比较）：flat 4/20（20%）、oracle 分页 17/20、
> BM25 分页 16/20、错块 1/20。绝对数漂移来自 `n_predict`/模板差异；**可比的只有同配置下的相对关系**，
> 而那个关系已经饱和。

### 4.2 M2 —— 放置规划器

**接口**：`plan(blocks, chat_start, budget) -> [(seq, target_pos)]`

必须解决的四个问题：

1. **预算**：`sum(n_blocks) + chat_len ≤ 8192`；且按 L10，**挂载块的总量应 ≤ ~4000**
   （否则最远的块距离 > 8k，挂了也读不到 → 白占 VRAM）。
2. **顺序**：按相关度/时间排序，最相关的**紧贴对话**（距离最短）。
3. **中途插入**（关键）：对话已经长到 5000 了，又来一块怎么办？
   - 可用原语：`seq_repos_local` **对任何序列都有效，包括对话本身**。
   - 步骤：`seq_rm(chat, 块区间)` 摘掉所有块的引用 → `repos_local(chat, +n_new)` 把对话整体上移
     → 新块 `repos_local` 到刚空出的 `[旧 chat_start, +n_new)` → 全部重新 `seq_cp`。
   - 注意：**必须先摘引用**，否则移动对话会把块一起拖走（L7 陷阱 2）。
   - 成本：对话 5000 token ≈ 5000/50 × 42 ms ≈ **4.2 s**（一次性，可接受但要有预算上限）。
4. **淘汰**：超预算时按 LRU / 相关度踢掉最远的一块（`seq_rm` 即可，文件不动）。

**验收**：3–5 块并发；对话进行到第 10 轮后插入一块新记忆，答案仍然正确；
插入前后未参与移动的块 0 字节变化。

### 4.3 M3 —— 块生命周期管理器

- **pin/refcount**：块被对话引用时不能 `reset` 源 seq（否则引用计数悬空）。
- **保存时机**：块一旦被旋转，磁盘文件就不再等于内存（文件是"position 0 的权威版本"）。
  → 决定：**文件只读**，永不回写；需要回到 0 位就**从文件重新加载**。
  （原稿写的是"再旋转一次即可，可逆"——**已证伪**：见 L3b，约 10 次往返后数值就坏了。）
- **碎片**：位置连续 ≠ cell 连续（批量搬运已支持多个连续段），但要监控 cell 池余量。
- **验收**：attach/detach 50 轮，`pos_max`、answer、cell 占用三者稳定，无单调上升。

### 4.4 M4 —— 写入固化（consolidation）

现在"哪些内容值得成为一块记忆"是**人**决定的（`MEMORIES` 常量）。要自动化需要：

1. 分段：按话题/时间切段，目标段长 ~500–1000 token（受 L10 约束，段不能太大）。
2. 判据：什么值得记？（用户陈述的事实、承诺、偏好；忽略寒暄）
3. 写入：`write_at(seq, text, 0)` → `save` → 插 SQLite（**编码时必须独占 position 0**，见 L6）。
4. 验收：一次对话后自动沉淀 1 块，**新进程**能检索并正确回答。

### 4.5 M5 —— 接地与弃答

`车牌号 → A-4417` 说明模型不会说"不知道"。缺一个**事后校验**（不是 prompt 注入）：
答案里的实体/数字是否出现在**被挂载块的正文**里？（正文可以留在 SQLite 旁边专供校验，
不进 prompt，不违反红线 2 的"索引不存正文"——校验用的副本是另一张表。）
不在 → 标红/重写为"未记录"。**验收**：控制题不再编造。

### 4.6 建议的推进顺序

```
M1 索引（已达标，待接入）──▶ M2 规划器 ──▶ M3 生命周期 ──▶ M4 写入 ──▶ M5 接地
   ↑                              ↑
   └─ 可并行 ─────────────────────┘（M2 的接口先定，用假数据跑通）
```

理由：M1 决定"取哪些块"（**已解决：facet = oracle**），M2 决定"放哪里"，两者接口一对齐，
整个系统就闭环了。M3 是稳定性，M4/M5 才是"仿生"的部分——**没有 M2/M4，M5 没有意义**。
注意：M1 的剩余工作不是"更准"，而是"接进 `chat.py`"——`facet_budget.py` 现在还只是个实验脚本。

## 10. Memory Contract（P0-1a 交付物）

### 10.1 三层，只有一层是真相

```
memory_source          源文本          ← 权威。不可变，永不进 prompt
     │                                    (r"trend" 只用于 rebuild / 接地校验)
     ├──▶ memory_block  .kvmem 状态文件   ← 派生。**是缓存**，可删可重建
     └──▶ facet index   指针 + facet      ← 派生。也只存指针，不存正文
```

**为什么必须这样**：块是有损且会磨损的（L3b：约 10 次 requantization 后开始崩），
而且绑定在某个模型/rope/kv 类型上。把块当唯一起源 = 模型升级或块磨损就永久丢记忆。
**块文件不是权威，是缓存**——这句话现在有实测支撑。

### 10.2 强制的不变量（不是靠自觉，是靠代码）

| 不变量 | 实现 | 验证 |
|---|---|---|
| `memory_source.text` 不可改 | SQLite `BEFORE UPDATE OF text` 触发器 `RAISE(ABORT)` | `p0_1a_check` 断言 UPDATE 抛错 |
| 同文本重复写入幂等 | `put_source` 按 `sha256(text)` 查重 | 断言两次返回同一 id |
| 换文本 = 新行 | append-only；旧块仍指向它当初的文本 | 同上 |
| 块与模型绑定 | `memory_block` 存 model_path/size/mtime/kv_type/state_version | 篡改 mtime → `Incompatible` |
| 加载失败要报错，不能当空 | `KVEngine.load_strict()`：`kvshim_load < 0` → 抛 `Incompatible` | 引擎拒绝时不再静默 |
| 块可丢、记忆不可丢 | `rebuild()` 删文件、从 source 重编码，**断言 token 数不变** | 4/4 答案逐字相同 |

> 注意：**不要求字节一致**。重建后的量化/位置可能与原来不同，但 token 数与答案必须一致——
> 前者是缓存的一致性，后者是记忆的一致性。

### 10.3 fallback 语义（写死，不再含糊）

| 阶段 | 失败时允许做什么 |
|---|---|
| **preflight 拒绝**（模型不支持：`rope_freqs` / `n_rot≠n_embd_head_k` / 块大小不整除）| 可以退回 `seq_add`。此时**零副作用已实测**：K 字节、pos、seq 位图、shift 全不变（`p0_1a_check` 在 layer 0/14/27 三处注入故障验证）|
| **写循环开始之后** | **禁止退回 `seq_add`**。只能从 pristine 文件重载，或从 source 重建。否则旧 bug 会以另一种形式回来：调用方以为失败可重试，实际上块已经转过一次 |

这条用代码结构保证：`return 0` 只可能出现在写循环之前（入口守卫 / 空 idxs / preflight），
写循环内只剩 abort 型断言，函数末尾必定 `return idxs.size() > 0`。

### 10.4 固定 slot 与 L4 的冲突（M2 前必须先解决）

固定 slot 的动机是 L3b：既然每次移动都在磨损，就不能"为了腾位置把对话整体搬一遍"。
**但 slot 尾部 padding 会在块尾和对话头之间造出一个洞，而 L4 说洞 ≥1 就废。** 三条路：

| 方案 | 做法 | 风险 |
|---|---|---|
| **A. 编码时 pad 到固定桶长** | 块本身含 padding，chat 紧贴 slot 尾 | 稳定方案；代价是几档固定长度（64/128/256/512）|
| **B. 固定 chat anchor，块向下紧贴** | 洞留在最底部 | 必须先证"底部洞无害"——这就是 P0-4 |
| C. 用 chat 的 padding token 填洞 | 洞被对话 token 占满 | 最后选，可能污染对话语义 |

**顺序：先做 B 的 hole 实验（P0-4），A 作为稳定方案。不要先写 slot 再发现 L4 不答应。**

**P0-4 已给出答案（§3.1 L4-D/E）：B 可行，而且可以做得比 B 更省——B-right。**
致死条件比想象的窄：只有"紧贴对话头、且对话自己看不见的空位"会致命。
B-right 把每个块在其 slot 内**右对齐**（块尾贴 slot 尾，顶槽块尾贴 chat anchor），
所有洞都落在块下面/块之间，于是**没有致命洞，也不需要 guard**（`p0_4b_right.py` 9/9）。

于是 §10.4 的三条路收敛为：

1. **B-right（采用）**：右对齐 slot。洞在块下与块间，矩阵证明无害；顶块贴 anchor。
2. **A（保留）**：编码时 pad 到定长桶，布局零洞。作为 B-right 出问题时的稳定退路。
3. **C（放弃）**：往对话里塞 padding 污染 context，B-right 已经够了。
4. **guard（仅兜底）**：只在"顶块无法贴住 anchor"（例如块比 slot 长、或 slot 数变化）时启用，
   契约见 §10.8。

#### 10.8 `layout_guard` 契约（仅当兜底启用时）

guard 不是普通记忆块，也不是无源 legacy 填充物，而是**物理上是块、语义上是布局产物**：

| 维度 | 规定 |
|---|---|
| 存储 | 是块：token、K/V、文件、hash、token 数俱全，可重建 |
| 语义 | `kind=layout_guard`、`retrievable=false`；不进 facet 索引，不出现在用户记忆列表 |
| provenance | 独立 spec（filler 文本、token 数、model/version、生成规则），**不是**无源 artifact |
| manifest | `role=guard` + 目标区间 + token 数 + block hash；restore 时校验并重挂 |
| 生命周期 | 可随时丢弃/重建，不 pin 成长期记忆；**被对话引用期间必须 pin 住** |
| 容量 | 计入 cell/VRAM 预算；**不计入"记忆条数"** |
| verify | 单独 `layout` 桶；legacy 的定义仍是"有块、无 provenance" |
| 硬要求 | 必须 `share` 给对话序列——"被别的 seq 占着"不够（`hole_probe.py` 用例 A vs D 已证） |

### 10.5 会话的权威在哪里（P0-2：detach-before-save + manifest）

**选择 detach-before-save，不做 token 账本。** 理由是本体一致：块是缓存，源文本是权威；
一个会话是"对话 + 一组布局引用"，不是"一个带记忆的 KV 大对象"。账本会把 token 语义塞进
`seq_cp`（今天是纯引用计数），之后每次共享/移动/保存都要维护它——把复杂度放在最不该放的地方。

```
保存：quiesce → detach（drop 掉 chat 对块 cell 的引用）→ 存纯对话 → 写 manifest → reattach
恢复：校验 manifest → load chat → 逐块 load_strict → 校验 token 数 → repos_local 到 target
      → seq_cp → 校验 pos_max → 才允许生成
```

manifest **分两层**，不能压成一张扁平列表：

| 层 | 内容 | 作用 |
|---|---|---|
| **layout（契约）** | `anchor`、`alignment`、`slot_capacity`、`guard_policy`、`planner_version`、slot 列表（`base`/`capacity`/`end`/`block`/`role`）| 恢复时**重新求位置**、校验不变式 |
| **placement（渲染）** | 每块 `start/end`、`slot_id`、`role`、`n_tokens`、block sha256；`chat_range`；`guard` 区间 | 审计、快速比对、发现"重算结果≠存档结果" |

另有 `chat`（state 文件名 / n_tokens / start / end）、model 指纹、kv_type、state_version、
saved_at、tenant/scope。

**恢复顺序**：读 layout → 用 token 数重新 `resolve` 出区间 → 与 placement 逐块比对 →
再校验不变式 → 不一致 **fail closed**。只存渲染就没资格判断"顶块是否真的贴住 anchor"，
而那正是 P0-4 唯一证明会致命的地方。

恢复时校验的不变式（`session_state.check_layout` / `check_placement`）：

1. `n_tokens <= slot.capacity`；
2. `block.end == slot.end`（右对齐）；
3. `slot[0].end == anchor`，且 `block[0].end == anchor`（头顶无不可见空位）；
4. 块之间不重叠、顺序自上而下；
5. slot 之间无缝（洞只允许出现在 slot 内部，即 base 与块头之间）；
6. `chat_range.start == anchor`（dialog 头无洞）；
7. 若有 guard：`role=guard`、覆盖 `[top_block.end, anchor)`、且已 `share` 给对话。

#### 10.5.2 M1-lite：按 facet 选块（`retrieval.py` / `eval_retrieval.py`）

选块是数据库问题，不是模型问题——整条链路不加载模型，避免把生成噪声折进选择信号。

索引是派生缓存（`facet` / `term` / `doc` 三张表，可从 `memory_source.text` 重建），
打分分三层：BM25（CJK 二元组 + 拉丁/数字）、实体精确命中、查询类型路由
（工号→id 面、什么时候→date 面）。多子句查询按标点/和/以及拆开，各子句独立过闸后取并集。

**闸门是两层**：`bm25 >= 1.30` 或 `覆盖率 >= 0.35`。覆盖率 = 命中词 idf / (命中 + 缺席×idf_absent)，
它挡住的是"只共享了'我的'这种常用词"的假命中。

固定 eval 集：10 块 / 19 问（10 单块、4 多块、5 缺席），BM25 与 facet 共用分词、语料、
闸门与 tie-break，只差打分函数：

| 打分 | recall@1 | recall@3 | recall@5 | MRR | 缺席→空 |
|---|---|---|---|---|---|
| BM25 | 0.893 | 0.964 | 0.964 | 1.000 | 5/5 |
| facet | 0.893 | **1.000** | **1.000** | 1.000 | 5/5 |

**诚实说明**：facet 的增量只有 +0.036 recall@3，其余持平。真正的提升来自停用二元组、
子句拆分、覆盖率闸门——这三项在两条臂里**共用**。所以"facet 打败 BM25"这个说法在这套
语料上证据很薄；能说的是它没变差，且实体命中在多块/多子句场景下更稳。
另外 `GATE` / `COV_MIN` / `REL_CUT` 三个阈值是在这同一套 eval 上调的，**有过拟合风险**，
下一步需要一套没调过的留出集。

**M1 的 no_evidence 已按三态实现**（`evidence.py`）：`memory_hit` / `chat_only` /
`no_evidence`。`no_evidence` 再按意图分流——记忆回忆类在**生成前拒答**（模型不调用），
常识类正常生成并打标。

拒答是应用层固定文案，**从不进入 `ask`**，所以 prompt 仍然只有问题。红线按两条记：

- **R1（记忆红线）**：记忆内容只以 KV 块挂载，永不进入 prompt——未变；
- **R2（应用文本）**：固定、非用户、非记忆的文案允许存在于应用层；每轮记
  `chars_injected`（拒答轮恒为 0）与 `policy_version`。

#### 10.5.4 M1.5：三个结构缺口（`analysis.py` 是新的分析链）

统一分析链 `analysis.py`（`ANALYSIS_VERSION = 1`），索引版本升到 2，索引仍可从
`memory_source` 全量重建——没有引入任何不可重建的第三方分词状态。

**缺口一：中文断词。** `几点` 和 `12点半` 不是同义词，是"**问一种值**"和"**给一种值**"。
所以 `answer_type(query)` 判查询要什么值，`value_kinds(text)` 判块里有什么值；
两者对上才准入。归一化（NFKC、中文数字时间/日期转阿拉伯、CJK 间空格合并）在两侧共用。
大二元组全不命中时，用**稀有 CJK 单字**兜底（`u:` 前缀），且兜底时覆盖率按**兜底表示**
重新计算——否则缺席的大二元组会把覆盖率压到 0，兜底等于白做。

**缺口二：属性级缺席。** 值类型闸门先筛"能答这个问题的块"：`我每个月工资多少` 要
money，而 money 模式要求 `元|块|万`，块里只有"15号发工资"→ 全灭 → 拒答（此前会答
finance+banking）。**故意不对称**：`name` 不做闸门，因为"负责人是周敏"没有 `叫`，
没有 NER 就检测不可靠；改用角色词（负责人/供应商）走词面，实测更稳。

**缺口三：chat_only 以 KV 为准。** 用户陈述用 `write_at` 无解码写进 chat KV；
**拒答文案不写入 history**（它从未进入 KV，若算作对话证据就又是应用层自嗨）。
判据降为"共享 1 个内容二元组"——方向是单向的：误判 chat_only 只是用对话回答，
误拒则是拒绝用户刚说的事实。

| 指标 | M1 | M1.5 |
|---|---|---|
| dev 19：recall@3 / MRR / 缺席 | 1.000 / 1.000 / 5-5 | 1.000 / 1.000 / 5-5（未退化）|
| 30 集：recall@1 / @3 / MRR | 0.762 / 0.952 / 0.921 | **0.810 / 1.000 / 0.968** |
| 多块全中 | 6/6 | 6/6 |
| 缺席 abstain / precision | 5/6 / 1.000 | **6/6 / 1.000** |
| chat_only | 1/3 | **2/3**（0 误拒、0 误挂）|

唯一残留：`我下周去哪出差` → travel（memory_hit）。**标注争议**：块确实与出差相关，
判 memory_hit 不算错；且该句没有事实名词，意图被判为 general。

**这 30 集从此是 dev，不是留出。** M1.5 是在它上面开发的，1.000 是 dev 数字。
无偏数字只能来自封存的 `holdout_50.py`。

#### 10.5.1 restore 的确定性边界（已实测归因）

"恢复后逐字不同"曾被当成待查项。`variance_check.py` 按"先比 K、再比文本"把它分完了，
结论是 **class 2（数值），不是 class 3（状态/布局）**：

| 项 | 结果 |
|---|---|
| block K/V | **逐字节相同**（两块 state 文件 hash 相同，位置相同）|
| block 重转次数 | 2 vs 2 —— **没有多花一次重量化** |
| chat token | 相同（文件头 + token 数组全等）|
| chat K/V 负载 | **字节多重集完全相同**，只是 cell 顺序被置换 |
| 事实取回 | 原会话 4/4，恢复 4/4 |
| 逐字相同 | 1/4（第 1 问相同，第 2 问起分叉）|

机制：恢复后 seq 0 的 cell 索引重新分配，K/V 内容不变而行顺序变了；注意力对行序数学
不变，但 GPU 归约按固定顺序求和，**浮点求和顺序变了** → logits 有极小差异 → 上下文
积累到一定程度才翻 argmax。

所以契约是：**恢复内容精确，不是布局精确**。承诺事实、位置、token 数、磨损次数；
不承诺逐字相同。M1 验收里加一条"save/load 后 retrieval@k 不塌"，让真实链路继续验。

两条工程教训：

1. **不能用整文件 hash 校验恢复**——state 文件按 cell 索引排序，恢复后索引重排，
   98% 的字节会"不同"而内容其实一样。要么按 position 排序后再比，要么比多重集；
2. 比文本之前先对齐**对话前缀**。我第一版拿"还没问过 4 轮的会话"去比"已经问过的恢复
   会话"，差异全是自己造的。

`p0_2_check.py` **22/22**，其中 [5] 专门做反向验证——三种篡改必须被拒：
改渲染区间（重算对不上）、整体上移 2 格伪造"头顶洞"（渲染自洽但违反不变式 3）、
删掉必填字段（schema 校验）。

三条实测（`p0_2_check.py` 17/17）：

| 验收 | 结果 |
|---|---|
| 带 2 块会话 save → **新进程** restore → 4/4 答案 | 逐字相同；chat 窗口 `4299 == 4299`；块区间原样；**每块恰好 1 次 shift** |
| 保存失败注入（`eng.save` 抛异常）→ 会话可重挂 | 布局未变（`pos 4264→4264`、`n 169→169`），仍答对；`finally` 里 reattach |
| 恢复后再聊一轮再 save → 账本不增长 | chat **203 tokens / 203 位置**、二轮 **372 / 372**：token 列表与位置跨度严格相等，块 token 没混进去 |

**一个意外的好处**：因为恢复总是从 pristine 文件重载，**磨损不跨会话累积**——每个会话都从
同一份字节开始，只有会话内反复重放（M2 的槽位移动）才消耗 L3b 的预算。detach-before-save
顺带把 L3b 的风险限制在"单会话内"。

### 10.6 派生层的三种状态（P0-1b）

一个永远只说"正常"的检查器不是仪器。`verify()` 现在分桶（`p0_1b_check.py` 15/15）：

| 状态 | 含义 | 允许做什么 |
|---|---|---|
| **managed** | source + block 一致、文件在 | 正常读写，可重建 |
| **unbuilt** | 有 source，还没编码 | 不是坏块，是待做的工作 |
| **legacy** | 有块、没有 source（旧版本留下的）| **只读**。文本已丢，**永远无法重建**——这正是 source 层要消除的代价 |
| **orphan** | 索引有、文件无 | **fail closed**，拒绝挂载（否则加载成空序列然后幻觉）|
| **broken** | 文件在但大小不符 | 拒绝挂载，从 source 重建 |

历史块按你的要求**只标 legacy，不做全量 backfill**；迁移等 P0-2 稳定后再补。

### 10.7 封版接缝登记（seam）

| 项 | 内容 |
|---|---|
| 名字 | `LLAMA_KV_REPOS_FAULT_LAYER`（`llama-kv-cache.cpp`，preflight 内）|
| 能力 | **只拒绝**。不能跳过旋转、不能改位置、不能吞错误 |
| 位置 | 入口读一次（lambda 初始化），**不进写循环、不进热路径、不分配**；默认关闭时只花一次 `getenv` |
| 可见性 | 触发时必打 `LLAMA_LOG_WARN`，并明说"这个 0 是注入的，不是能力上限" |
| 回归 | `p0_2_check.py` 的 `[0]`：unset 时 `moved 50/50`，行为不变 |
| 为什么留 | 本模型永远走不到 `rope_freqs` / `n_rot != head_dim` 分支，没有接缝这条安全路径**无法被测**，而未测的安全路径会腐烂 |
| 何时重议 | QQ / 多租户 / 分发阶段，若封版标准要求"生产二进制零测试接缝"，再移到测试构建 |

机制：恢复后 seq 0 的 cell 索引重新分配，K/V 内容不变而行顺序变了；注意力对行序数学
不变，但 GPU 归约按固定顺序求和，**浮点求和顺序变了** → logits 有极小差异 → 上下文
积累到一定程度才翻 argmax。

所以契约是：**恢复内容精确，不是布局精确**。承诺事实、位置、token 数、磨损次数；
不承诺逐字相同。M1 验收里加一条"save/load 后 retrieval@k 不塌"，让真实链路继续验。

两条工程教训：

1. **不能用整文件 hash 校验恢复**——state 文件按 cell 索引排序，恢复后索引重排，
   98% 的字节会"不同"而内容其实一样。要么按 position 排序后再比，要么比多重集；
2. 比文本之前先对齐**对话前缀**。我第一版拿"还没问过 4 轮的会话"去比"已经问过的恢复
   会话"，差异全是自己造的。

`p0_2_check.py` **22/22**，其中 [5] 专门做反向验证——三种篡改必须被拒：
改渲染区间（重算对不上）、整体上移 2 格伪造"头顶洞"（渲染自洽但违反不变式 3）、
删掉必填字段（schema 校验）。

三条实测（`p0_2_check.py` 17/17）：

| 验收 | 结果 |
|---|---|
| 带 2 块会话 save → **新进程** restore → 4/4 答案 | 逐字相同；chat 窗口 `4299 == 4299`；块区间原样；**每块恰好 1 次 shift** |
| 保存失败注入（`eng.save` 抛异常）→ 会话可重挂 | 布局未变（`pos 4264→4264`、`n 169→169`），仍答对；`finally` 里 reattach |
| 恢复后再聊一轮再 save → 账本不增长 | chat **203 tokens / 203 位置**、二轮 **372 / 372**：token 列表与位置跨度严格相等，块 token 没混进去 |

**一个意外的好处**：因为恢复总是从 pristine 文件重载，**磨损不跨会话累积**——每个会话都从
同一份字节开始，只有会话内反复重放（M2 的槽位移动）才消耗 L3b 的预算。detach-before-save
顺带把 L3b 的风险限制在"单会话内"。

### 10.6 派生层的三种状态（P0-1b）

一个永远只说"正常"的检查器不是仪器。`verify()` 现在分桶（`p0_1b_check.py` 15/15）：

| 状态 | 含义 | 允许做什么 |
|---|---|---|
| **managed** | source + block 一致、文件在 | 正常读写，可重建 |
| **unbuilt** | 有 source，还没编码 | 不是坏块，是待做的工作 |
| **legacy** | 有块、没有 source（旧版本留下的）| **只读**。文本已丢，**永远无法重建**——这正是 source 层要消除的代价 |
| **orphan** | 索引有、文件无 | **fail closed**，拒绝挂载（否则加载成空序列然后幻觉）|
| **broken** | 文件在但大小不符 | 拒绝挂载，从 source 重建 |

历史块按你的要求**只标 legacy，不做全量 backfill**；迁移等 P0-2 稳定后再补。

### 10.7 封版接缝登记（seam）

| 项 | 内容 |
|---|---|
| 名字 | `LLAMA_KV_REPOS_FAULT_LAYER`（`llama-kv-cache.cpp`，preflight 内）|
| 能力 | **只拒绝**。不能跳过旋转、不能改位置、不能吞错误 |
| 位置 | 入口读一次（lambda 初始化），**不进写循环、不进热路径、不分配**；默认关闭时只花一次 `getenv` |
| 可见性 | 触发时必打 `LLAMA_LOG_WARN`，并明说"这个 0 是注入的，不是能力上限" |
| 回归 | `p0_2_check.py` 的 `[0]`：unset 时 `moved 50/50`，行为不变 |
| 为什么留 | 本模型永远走不到 `rope_freqs` / `n_rot != head_dim` 分支，没有接缝这条安全路径**无法被测**，而未测的安全路径会腐烂 |
| 何时重议 | QQ / 多租户 / 分发阶段，若封版标准要求"生产二进制零测试接缝"，再移到测试构建 |
