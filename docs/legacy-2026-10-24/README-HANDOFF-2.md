## 1. 本轮完成的实验（✅ 已做，不要重做）

### 1.1 context-shift 会不会毁掉记忆

工具：`tools/kvmem_persist.cpp` 的 `shift` 子命令；脚本：`tools/test_shift.ps1`。
做法：先恢复记忆（69 token，pos 0..68），再用 900 token 闲聊填满对话区，
然后**完全照 `server-context.cpp:3698-3699`** 做一次 shift，只变 `n_keep`。

| n_keep | n_discard | 实测结果 |
|---|---|---|
| 69（= 记忆长度） | 0 | 答对（填充本身无害） |
| 69 | 300 | 答对，记忆仍在 0..68，对话 pos_max 968→668 |
| **0（server 默认）** | 300 | `____。` **答错** |
| 0 | 69 | 答错（整段记忆被丢） |
| 0 | 1 | **仍答对，但记忆已被静默下移 1 位、掉了头一个 token** |

**机理**：shift 分两步，`n_keep` 默认 0，丢弃区间从 pos 0 开始：

```
seq_rm (id, n_keep, n_keep + n_discard);                // 第一步就删"归属"
seq_add(id, n_keep + n_discard, pos_next, -n_discard);  // 其余整体左移
```

记忆是靠 `seq_cp` 挂在对话 seq 上的 0..68，第一步就把"对话看得见记忆"删掉了。
server 默认 `n_discard = n_left/2`，900 token 的对话一次 shift 丢 300，**正好整段抹平**。

**三条可直接用的结论**：

1. **一行止血**：集成时 `n_keep = max(user_n_keep, mem_len)`。
2. **但不能只靠约定**：`n_discard=1` 那行证明越界**不报错**，只会静默移位/截断。
   所以 `pinned`（§README-HANDOFF 4.6）仍然要做 —— 它把"记忆不进可丢弃区间"
   变成数据结构里的不变量，而不是调用方纪律。
3. **`seq_pos_min == 0` 不能用来判断记忆是否还在**：shift 会把闲聊 cell 搬到 0..，
   这个指标会假阳性。唯一可靠判据是问答结果。

### 1.2 顺带确认的两个容量事实

- 非 unified：`n_ctx_seq = n_ctx / n_seq_max`（再 pad 到 256 的倍数）。
  `n_seq_max=8` + `n_ctx=1024` → 每条 seq 只有 128 个 cell，900 token 直接报
  `failed to find a memory slot`。**记忆系统的 `n_ctx` 要按"每 seq 容量 × seq 数"算。**
- `--unified`（`cparams.kv_unified=true`）：`n_ctx_seq = n_ctx`，所有 seq 共享一个池。
  保存 / 恢复 / `seq_cp` / shift 的行为与上表**完全一致**。
  **做 100k 记忆应该用 unified**，否则容量会被 `n_seq_max` 除一遍。

## 3. 路线论证：到底能"改"哪一层（本轮最重要的一节）

### 3.1 三层，边界由"权重有没有训过这条路"决定

| 改什么 | 权重动吗 | 现成 GGUF 可用 | 代表 |
|---|---|---|---|
| **推理期机制**：mask / 位置 / KV 注入 / 门控 / 调度 | 不动 | ✅ | 我们正在做的 L0/L1 |
| **加小模块**：编码器 / 门控 / 记忆库 | 主模型冻结，训 ~1% | ✅ | ICAE、Gist、Memorizing Transformer |
| **改架构**：新增记忆层 / 交叉注意力 | 必须继续预训练 | ❌ | Titans、MemoryLLM |

### 3.2 为什么"塞 KV"免费，"加一层"必须训

- 塞 KV（`seq_cp` 或 embd 注入）走的是模型**已经训过**的通路：对 attention 来说
  位置 0..M 的 K/V 就是"前文"。**M1 已经实证：69 token，零梯度，答对。**
- 新增记忆交叉注意力是**没见过的通路**，随机初始化 = 往残差流灌噪声，
  不训就是纯噪声；训就得按"卡·月"算。

一句话：**改"已有通路的输入"免费，加"新通路"要训。**

### 3.3 训练成本（可复核，别信感觉）

`FLOPs ≈ 6 × 参数量 × token 数`；单卡 24GB 有效吞吐按 **30 TFLOPS** 估（偏乐观，QLoRA 更低）。

| 目标 | token 量 | FLOPs | 单张 24GB 用时 |
|---|---|---|---|
| LoRA 改行为/指令遵循 | 1×10⁷ | ~4×10¹⁷ | **约 4 小时** |
| 记忆编码器（ICAE 级，起步规模） | 1×10⁸ | ~4×10¹⁸ | **约 1.5 天** |
| 继续预训练并加记忆层 | 1×10¹⁰ | ~4×10²⁰ | 约 5 个月 |
| 正经继续预训练 | 1×10¹¹ | ~4×10²¹ | 约 4.5 年 |

7B 本体那两行就是"不做"的理由：不是做不到，是做不完。
**能被个人项目碰的只有前两行。**

### 3.4 结论

- **7B 不训。** 它只做前向，权重一个字节不动。
- **要训就训 1%**：编码器（~50M，新增）+ LoRA（~10–20M，贴在 attention 投影上）。
- 训完产物是**几十 MB 的 embedding 权重**，不是新模型；推理端仍是那个 4.36GB 的 GGUF。

## 5. 训练方案（已设计，**未实施**）

### 5.1 结构

```
文档 token ──(冻结的 7B embedding)──> 编码器(几层 transformer + K 个可学 query)──> K 个槽向量
                                                                                  │
问题 token ────────────────────────────────────────────────────────────────────────┤
                                                                                  ▼
                                            7B(冻结, q4) 一次前向 ──> 答案
```

- 只训练编码器（+ 可选 LoRA）；损失只算在答案 token 上。
- 槽向量必须落在 7B 的 embedding 空间（d=3584），才能被当"前文"读。

### 5.2 怎么接回 llama.cpp（关键，别绕路）

1. 编码器在 PyTorch/ONNX 里跑（**不放进 llama.cpp**），输出 K×3584 的 float 向量。
2. 用 `llama_batch.embd` 喂给 7B（llama.cpp 原生支持 embedding 输入，
   多模态 `mtmd` 就是这么做的），得到与"真的读了这段文字"等价的 KV。
3. 这份 KV 用**已有的** `llama_state_seq_get_data/set_data` 落盘 —— 第 1 步已经验证过的通道。
4. 之后所有会话 `seq_cp` 共享，零成本。

**要点：不需要给 llama.cpp 加新 API。** 编码在外部，注入用 embd，持久化用现成 state API。

### 5.3 验收标准

同一段 8k token 文档，压成 256 个槽后答题准确率 **≥ 全塞上下文的 90%**。
（这条是上一轮定的，沿用。）

### 5.4 数据与成本

- 1–5 万条（文档 → 问题）对；可用本地 7B 自己合成（预填充 655 t/s，几小时造完），不必买数据。
- 24GB 卡、seq 4096、q4 冻结底座 + LoRA r=16 + 梯度检查点：约 2–3 s/step，
  1 万步 ≈ 8 小时 ≈ **$3–5**（Vast/RunPod）。
- 备选：Kaggle 免费 2×T4 16GB（30h/周），seq 降到 2048、断点续训，慢一倍。

### 5.5 风险（必须让用户知道）

- 成功率估计 **五到七成**，不是保证。ICAE 的 4× 是在 Llama 上成立的，
  换到 Qwen2.5 蒸馏版 + 用户数据要重测。
- ScopeMem 的反例说明：训出来的模块可能"修好一些、弄坏另一些"，只看平均分会骗人，
  **必须按题型分组看**。

### 6.1 选项 A 已执行：结论推翻了"100k 平铺记忆"的前提

工具：`tools/kvmem_quality.cpp`（新）、`tools/make_quality_set.py`、`tools/grade_quality.py`、
`tools/recall_curve.py`、`tools/run_quality.ps1`。语料 20 条植入事实 / 20 问 / 5 个深度段。

**第一组（rev A，语料 `quality/revA/`，5,424 token）—— 机制等价性，四臂逐题完全相同：**

| 臂 | 结果 | 说明 |
|---|---|---|
| `full` f16 | 17/20 (85%) | 全塞上下文（基线/分母） |
| `full` q8_0 | 17/20 (85%) | 生产 KV 类型，零损失 |
| `kv` f16 | 17/20 (85%) | **KV 记忆 == 全塞上下文** |
| `kv` q8_0 | 17/20 (85%) | 同上 |
| `none` | 1/20 (5%) | 控制组；那 1 题是"花粉过敏→氯雷他定"的常识蒙对 |

三点确认：① 记忆臂与基线**逐题同错同对**（答错的都是青岛→上海、琥珀书店→图书馆、
三点半→星巴克，即"世界常识压过文档"）；② `q8_0` 在 5k 规模零代价；
③ 速度：20 问，全塞上下文 **740 s**（每题重预填 37 s）vs KV 记忆 **62 s**
（32 s 一次性预填 + 每题 ~1.5 s）→ **约 24×**，且记忆可跨进程复用。

**第二组（语料 `quality/doc_5k|20k|100k`，同一生成器）—— 规模曲线：**

| 记忆长度 | 臂 | 召回 | 备注 |
|---|---|---|---|
| 5,439 token | kv f16 / q8_0 | 14/20 (70%) | 两种 KV 类型再次完全一致 |
| 19,597 token | kv q8_0 | 4/20 (20%) | 预填 400 s（49 t/s） |
| 96,770 token | — | **未跑** | 预填约需 80 min，趋势已定，不花这个时间 |

**召回率 vs 距离（事实离问题有多少 token）—— 这是本轮最有用的一个数：**

| 距离 | 0-1k | 1-2k | 2-4k | 4-8k | 8-16k | >16k |
|---|---|---|---|---|---|---|
| 召回 | 5/9 56% | 5/7 71% | 13/18 72% | 9/14 64% | **0/9 0%** | **0/3 0%** |

**这不是缓慢衰减，是断崖。** 约 4-5k token 之内正常（60-72%），到 8k 以外直接归零。
19.6k 那轮的 4 个命中全部落在距离 ≤ 4.5k 的尾部。

**这条结论直接推翻了 README 里的"常驻区 pos 0..64k"平铺设计**：位置 0..64k 的记忆，
模型只读得见最后 ~5k。mask 可见性（§4.1）解决的是"能不能看见"，解决不了"看得见但够不着"。
而且**加召回门控（L2a）也救不了** —— 屏蔽掉无关块不会把相关块变近，位置距离照旧。

**推论（下一步的设计前提）**：长记忆只有两条路，都必须让"要用的记忆落在问题前 ~4k 以内"：

1. **压缩（L2b）**：编码器把文档压成几百个槽，直接喂在问题前面的位置上。
   §5.2 的 `embd` 注入路径天然满足这一点 —— 槽是在目标位置被算出来的，没有位置迁移问题。
   **L2b 从"省显存/提速"升级为"唯一能让百 k 记忆被读到的机制"。**
2. **分页 + 位置重排**：把选中的块搬到窗口内。但 RoPE 让 K 依赖位置，
   搬动必须按位置差重旋转 K（`seq_repos` 一类的新操作），这是**引擎侧的新工作量**，
   不在原计划里。

**同时暴露的两个方法学坑（下一位别再踩）**：

- **20 题太粗**：单题 5%，两种语料同一构造下 70% vs 85% 的差异基本在噪声内。
  L2b 验收要 ≥60 题，且必须按距离分层看，不能只看总分（§5.5 的 ScopeMem 警告同理）。
- **合成填充要防"同质化"**：`revA` 用手写句池，`5k/20k` 用组合式模板（否则 100k 会重复同一段
  170 次）。组合模板更同质，可读性更高但更难检索 —— 这也是 5k 从 85% 掉到 70% 的主要原因之一。
  测召回时语料的"针叶密度"和"背景同质性"必须一起报告。

### 6.2 分页投放已验证：位置而不是容量（同日，§6.1 的直接后续）

§6.1 的断崖提出一个问题：既然 19.6k 平铺只能读到尾部，那**把需要的块搬到问题前面**能不能恢复？
工具：`tools/kvmem_page.cpp`。做法是把 20k 文档按段落切成 20 块（每块 ~1k token，
**每块都独立地从 pos 0 开始编码**，所以任何块都能塞进同一个窗口槽，不需要重算 RoPE、
不需要改引擎），每题的块号由 oracle 索引给定（题目 id == 段落号，无偏移误差）。

| 同一份 20k 文档、同样 20 题 | 命中 | 说明 |
|---|---|---|
| 全常驻、平铺 | 4/20 (20%) | §6.1 的老结果 |
| **按 oracle 索引取对块 → 灌窗** | **17/20 (85%)** | 与 5k 平铺的 17/20 持平 |
| **按真实索引取块（BM25，见 §6.3）** | **16/20 (80%)** | 端到端，索引只花掉 5 个点 |
| 取错块（`--wrong`，对照组） | **1/20 (5%)** | 与"无记忆"基线完全一致 |

**三个结论：**

1. **涨分全部来自索引，不来自"上下文变小"**。错块对照组掉回 5%，说明模型对错块
   完全不用，直接退回先验 —— 如果没有这个对照，"小上下文更容易"是个同样成立的解释。
2. **引擎一行不用改**。`seq_rm` + `llama_state_seq_set_data` 就够了，块加载实测 **0.01 s**
   （OS page cache 命中；冷读 29 MiB 约 0.1–0.3 s）。
3. **"常驻"≠"可读"**。19.6k 全在显存里只有 20%，窗口里 1k 却 85%。
   VRAM 容量不是瓶颈，**位置投放**才是。

**由此，整个项目的风险从"模型/训练"转移到了"索引"**：编码器训练（C，要租卡）
不再是关键路径；关键路径是一个**本机就能建、能调、能失败得明白**的检索索引。
这也顺带解释了为什么 §7 的红线在这里不构成障碍 —— 索引是数据结构，不是训练产物。

### 6.3 索引该长什么样（§6.2 之后的约束，待实现）

来自两个方向的一致结论：

- **内容单位是一段，不是一点**（§6.2 的块就是段落，~1k token）。
- **索引是多方向的指针**：时间 / 地点 / 参与者 / 事件类型 / 实体编号。
  这几条**大部分相关但不完全相同** —— 完全重合就退化成"一个索引五个名字"，
  完全不重合则无法交叉验证。有用区间在中间。
- 检索按"方向并集出候选 + 方向一致度排序"，而不是单条稠密向量的余弦。
  这直接针对 §6.1 观测到的串台（`0527→9031`、`泉州→杭州`）：多方向对不上时，
  错块的总分会被压下去。
- 索引条目只放指针与元数据，**不放内容**；内容永远是磁盘上的 `.kvmem`。
  这让索引可重建、可丢弃，也让 §7 的可移除性检查自动成立。

**下一个要测的数**：真实索引的 retrieval@1。§6.2 的 85% 是 oracle 上限，
若 real@1 只有 50%，端到端会掉到 ~45%，那就得先提高索引，而不是去训模型。

**已测（见 §6.4）**：字符 BM25 的 retrieval@1 = 19/20 (95%)，端到端 16/20 (80%)。
索引在这个语料上不是瓶颈 —— 但这个语料对字面匹配过于友好，结论不能外推。

### 6.4 索引下限：零依赖 BM25 就到 95%（同日）

`tools/retrieval_baseline.py`：字符二元组 BM25，无模型、无 GPU、无训练，
按"题目 → 20 个块"取 top-1：

```
retrieval@1 = 19/20 = 95%
```

唯一失手的是 `林知远在哪个部门？`（rank 5）—— 块里写的是"他现在**挂在供应链分析组**"，
和"部门"零词面重叠。这条恰好说明**两类失败模式是互补的**：

| 失败模式 | 谁擅长 | 表现 |
|---|---|---|
| 换了说法（部门 ↔ 挂在…组） | 稠密向量 / 多方向 facet | BM25 直接失手 |
| 多个相似事实互相污染（§6.1 的 `0527→9031`） | 多方向一致度 | 稠密向量容易失手 |

所以 §6.3 的多方向索引不是学术趣味，是这两条实测失败的共同解。

**但要诚实**：这个语料每个块只装一条事实、问题几乎逐字复用事实里的词，
字面匹配得分被系统性抬高。真实对话记忆不会这么友好，**95% 是上限不是预期**。

**另一个坑（本轮踩到）**：工具内建的打分是原始 `answer.find(expect)`，
`grade_quality.py` 会做全角/标点/空白归一化，两者对同一次运行会差 2 题
（15 vs 17）。**一律以 grader 为准**，否则会得出"端到端掉到 70%"这种假警报。

### 6.5 KV 槽位 + 无文本注入（Python 绑定，已跑通）

目标：记忆唤醒时**不经过任何 prompt 文本**，直接把它的 KV 二进制块装进引擎。
用的是 llama.h 里三个状态级接口，不是 prompt 拼接：

| 接口 | 作用 |
|---|---|
| `llama_state_seq_save_file(ctx, path, seq, tokens, n)` | 把某个序列的 KV + token 一起写盘 |
| `llama_state_seq_load_file(ctx, path, dest_seq, buf, cap, &n)` | 装回**任意**序列 id（两次调用：先问 token 数） |
| `llama_memory_seq_cp(mem, src, dst, p0, p1)` | 让 dst 引用 src 的 cell，**只加引用计数**，不拷贝 |

服务端自己也是这么实现的（`tools/server/server-context.cpp` 的
`SERVER_TASK_TYPE_SLOT_SAVE` / `SLOT_RESTORE` 分支，第 3141-3260 行），
即上面这两个 file 接口就是官方 slot 持久化的底层。

**实现**：`tools/kvshim.cpp` 暴露扁平 C ABI（全部是 int / char*），
Python 侧 `tools/kvslots.py` 用 ctypes 调用。不直接 ctypes `llama.h` 的原因：
`llama_context_params` 是按值传的结构体，字段偏移算错会静默损坏整个上下文。

运行：`python tools/kvslots.py --gpu 99 --kv q8_0 --ctx 8192 --slots 3`

**实测结果（全部 OK）**：

```
1) 三段对话同时驻留三个序列          A/B/C 各 15-24 tok，536/447/715 KiB
2) 逐槽写盘                          conv_A.kvmem 1,548.5 KiB（含问答），5-20 ms
3) 清空后冷问                        模型编造 "工号是12345"
   装进**另一个**序列 id (seq 3)     52 tok 恢复，正确答 "A-4417"
4) 第四段对话触发 LRU 淘汰           淘汰 A、写 D；再唤回 A 仍正确
5) 记忆作为独立序列 seq_cp 进对话     无记忆时编造 1234567890 → 注入后答 9031
```

**三条硬约束（都是本轮撞出来的，不是推出来的）**：

1. **位置是共享资源**，不是每序列独立。统一 KV 下两段不同内容都从 pos 0 开始写会互相
   覆盖 —— 第一版三题全错、18 token 存出 1.4 MB 就是这么来的。所以**每段记忆必须有
   自己的位置基址**（demo 用 stride 256），并且这个基址随文件一起保存，装到哪个
   seq_id 都不变。
2. **位置必须连续，一个洞都不行**。同一记忆、同一问题，把对话起点从 `+0` 推到 `+1`
   就变成空输出（+8/+64/+700 同样空）。这不是"距离变远导致召回下降"，是**生成直接
   崩掉**。根因还没定位（更像 KV 分配/掩码的不变量，不是模型行为），但结论明确：
   **记忆必须紧贴对话下方**。
3. **由此推出换块的代价**：换一个长度不同的块 → 对话起点必须跟着移动 → 对话的 K
   已在原位，只有两条路：(a) **重放对话 token**（对话只有几十 token，代价 ~0.2 s，
   不需要改引擎）；(b) **把记忆块按位置差**移**到对话正下方**。
   **更正：§6.6 证明 (b) 根本不需要改引擎** —— `llama_memory_seq_add` 已经实现了精确的
   rope 重旋转。当前 demo 走 (a)，(b) 的实测见下节。

**成本数字**：30,464 B/token（q8_0，与 §6.1 一致）；一段 18 token 的对话 = 536 KiB；
8k ctx 的池 = 238 MiB；1k token 记忆 = 29.8 MiB；100k token 记忆 ≈ 3 GB 磁盘。
存取延迟：save 5-20 ms，load 20 ms。

### 6.6 位置重排（选项 b）：引擎已经会，而且够快

上一节把"换长度不同的块"归给两条路，其中 (b) 我写成"要动引擎"。**错了，不用改引擎。**

`llama_memory_seq_add(mem, seq, p0, p1, delta)` 不是单纯改 position：它把位移记在 cell 上
（`llama_kv_cells::pos_add` → `shift[i] += d; has_shift = true`），下一次 decode 时
`llama_kv_cache::init_update` 看到 `has_shift` 就构建 `build_graph_shift`，用
`ggml_rope_ext` 把 K **就地重旋转**到新位置（量化 cache 走 dequant → rope → requant）。
这就是上下文移位背后的精确机制，llama.h 里一直有。

**实测（`kvslots.py` 第 6 段，q8_0 / 8k ctx）**：

| 项 | 结果 |
|---|---|
| 同一块：原生编码在 4096 vs 编码在 0 后位移 +4096 | **答案逐字相同** |
| 位置 | 都是 4096..4116 |
| 状态字节 | 1,799,028 B 中 **67.45% 不同** |
| 位移开销 | **~110 ms** |

三点解读：

1. **语义精确**：答案逐字相同，块可以被自由摆放。这正是"任意块塞进任意槽位"需要的能力。
2. **漂移只发生在被移动的那一块**：67% 的字节差不是"污染了别的序列"，而是这一块自己的
   K 多经历了一次舍入（原生：decode 时直接按 4096 转一次；移动：按 0 转一次、再按 +4096 转
   一次）。实测见 §6.7：**没被移动的序列 100 次位移后 0 字节变化**。
3. **开销与 ctx 成正比，与块大小无关**：8k 上约 40–65 ms，100k 上会到 ~0.5-0.8 s。
   好消息是 §6.2 已经把窗口压到 4-8k，所以这个代价**不会随记忆总量增长**。

### 6.7 反复位移不腐蚀常驻序列（已实测，q8_0 够用）

`build_graph_shift` 确实会重写整个 K 张量，所以必须回答一个问题：常驻的对话序列会不会被
一次次重新量化磨坏？`tools/kvdrift.py` 直接测：

```
python tools/kvdrift.py --gpu 99 --kv q8_0 --n 100 --checkpoints 0,100 --reload
```

- 一条常驻对话（3 个事实），每条 **placement = load + repos + flush decode**（真实每轮路径）
- 另有一条 `hold` 序列**从不过问任何问题**，只被动地经历重写，作为漂移见证

| 项 | 结果 |
|---|---|
| 100 次 placement 后对话 | 3/3 全对，**答案逐字未变** |
| `hold` 序列状态（1,463,748 B） | **0 字节变化（0.00%）** |
| 单次 placement 耗时（8k ctx, q8_0） | **52–65 ms**（含从磁盘 load） |

结论：**不需要 f16，也不需要定期重载**。原因是 q8_0 → f32 → q8_0 往返是幂等的，
而未被移动的 cell 位移为 0 时 rope 是恒等变换，写回去字节完全相同。漂移只存在于
被移动块自己的那一次舍入里，且不改变答案。

（上一版这里写的"其余序列也会被重新量化、建议改用 f16"是错的，已按实测改正。）

**由此定下的投放算法**（未实现，下一步）：

```
chat_start = pos_max(chat) + 1
target     = chat_start - n            # 块必须紧贴对话下方（§6.5 约束 ②）
repos(block, target - block_base)      # 先移位
seq_cp(block -> chat)                  # 再共享（顺序不能反）
```

顺序要注意：必须先 `repos` 再 `seq_cp`，否则位移会作用到已经共享的 cell 上，把对话
自身的位置也一起拖走。

## 7. 已定：红线边界（2026-10-24 用户拍板）

### 7.1 结论：允许"冻结 7B + 旁挂小模块"，判据换了

原条文（`README-HANDOFF.md` §1.2"不许换模型/重训才能生效"）按字面读，会把
"7B 冻结 + 训 1% 编码器"也一并禁掉。用户明确改了判据：

> **不看训练本身，看"是否需要训练才能跑通"。**
> 如果删掉训练产物，产品就交不出去，那才是变相重训。

按这条判据：

| 场景 | 判定 |
|---|---|
| L0/L1 独立能跑，编码器只是把 5k token 压成 256 槽 | ✅ 合规（渐进增强） |
| 没有编码器就跑不通主流程 / 答不对 | ❌ 违规（变相重训） |
| LoRA 合并进 GGUF 后发布 | ❌ 违规（模型文件变了） |
| 继续预训练 / 新增记忆层 | ❌ 明确违规 |

三条支撑事实：7B 权重字节不变（sha256 不变）；L0/L1 路径零训练产物即可跑通
（§2.4、§2.5 已实证）；编码器输出的仍是 KV，注入路径与第 1 步完全一致。
补充一条用户点出、我们之前没写下来的性质：**编码器只在"写入记忆"时跑一次**，
KV 算完就落盘、被所有会话 `seq_cp` 共享，查询时根本不需要它 ——
所以哪怕它只能跑 CPU、写一条记忆要 3 秒，产品体验也不受影响。

### 7.2 三条可机械检查的规则（写进红线）

1. **7B 权重文件不得修改**，发布物中其 sha256 与原版一致。
2. **任何训练产物（编码器 / LoRA / 门控）必须可移除**：删掉之后，
   系统仍能完成"写入记忆 → 重启 → 只问问题 → 答对"（即 `test_persist.ps1` 仍绿）。
3. **禁止把训练产物合并进模型权重**，禁止以"必须搭配某适配器"为交付前提。

这三条都能自动验证：对文件算 hash；删掉旁挂文件后跑一遍 `test_persist.ps1`。
比"允不允许训练"这种模糊表述好执行得多。

**已实现并跑通**：`tools/check_redline.ps1` 一条命令检查三条规则，退出码 0/1。
基线哈希已钉在 `tools/redline_model.sha256`：
`DeepSeek-R1-Distill-Qwen-7B-Q4_K_M.gguf` = `731ece8d06dc7eda6f6572997feb9ee1258db0784827e642909d9b565641937b`。
当前状态：**RED LINE: HOLDS**（R1 已入库，R2 用裸模型跑通三进程验收，R3 无从违反）。
以后每次交付前跑一次；一旦 R1 变红，说明有人动的不是旁挂文件，而是模型本体。

### 7.3 一个必须点破的越界点：LoRA 是红线最容易失守的地方

ICAE 原文训的是 **编码器 + 一个贴在 7B 上的 LoRA**（让 7B 适应"压缩过的前文"）。
如果没有 LoRA 编码器就不 work，那发布物其实是"7B + LoRA + 编码器"，不再是"现成 GGUF"。
LoRA 不合并、运行时加载，技术上模型文件没变，但**行为变了** ——
用户拿原版 GGUF 跑我们的服务会得到不同结果，这同样算越界。

**处理方式（按保守程度排）**：

1. 只训编码器，不碰 7B（最干净）。风险：效果可能明显差一截，**需要实测才知道差多少**。
2. LoRA 作为可选增益：默认路径无 LoRA 也要能答对，LoRA 只用于提升准确率，两个模式都发布。
3. 允许 LoRA 但禁止合并（上面那条的宽松版）。

**本轮决定：先按 1 试。** 如果编码器单独就能到 §5.3 的 90% 线，LoRA 根本没必要碰，
红线一点不模糊。§5.1 里"（+ 可选 LoRA）"和 §3.4 里"LoRA（~10–20M）"这两处措辞
**与本决策冲突，以本节为准**（§3.4 那句"7B 权重一个字节不动"和同段的 LoRA 本来就自相矛盾）。

1. **不要重做** §2.4（跨进程持久化）和 §2.5（shift 实验），两个套件都是绿的。

6. **不要回退到 prompt 拼接**（§1.1 红线）。所有"记忆"必须走 KV。
7. **清理临时文件**：`tools/*.kvmem` 是测试产物，可随时删（本轮结束时已清空）。

    20 行显示成 10 行（用 `-Encoding UTF8`，或交给 Python）。曾因此误判"结果被截断"。

12. **配置项别用 `_` 当分隔符**：`kv_q8_0` 会被 `-split '_'` 拆成三段。
    复用 `run_quality.ps1 -Configs` 时用 `:`。
13. **不要在半截文件上打分**：结果文件是逐题 flush 的，运行中读会得到中间值
    （曾据此得出"q8_0 掉 30 分"的错误结论）。等进程退出再看。

## 11. 引擎级补丁：seq_repos_local（局部 RoPE 重旋转）

本轮把 §6.6 的"移动块"从 shim 的 `seq_add` 黑盒换成了**引擎内自己实现的局部旋转**。
只改 `src/` 与 `include/`，`ggml/` 一行未动。

### 11.1 改了什么

| 文件 | 改动 |
|---|---|
| `src/llama-kv-cells.h` | 新增 `pos_move(i, d)`：与 `pos_add` 同样的 `seq_pos` 记账，但**不写 `shift[]`、不置 `has_shift`** |
| `src/llama-memory.h` | 新增虚函数 `seq_repos_local(seq, p0, p1, delta)`（默认返回 0）+ `set_cparams()` |
| `src/llama-kv-cache.h/.cpp` | 实现 `seq_repos_local`：只取真正移动的 cell，逐层按"连续区段"批量 D2H → 反量化 → **H → rope → H** → 量化 → H2D |
| `include/llama.h`, `src/llama-context.cpp` | 公开 `llama_memory_seq_repos_local()`；创建 memory 后注入 `cparams` |

关键点：
- **`pos_add` 不能用**。它置 `has_shift`，下次 decode 会再跑一次 `build_graph_shift` → 双重旋转。
  必须用 `pos_set`（但 `pos_set` 断言 cell 为空）→ 因此新增 `pos_move`。
- **旋转是同步完成的**，不留 pending shift，不需要 flush decode。
- 角度公式 `theta_j = pos * w_j`，`w_j` 只依赖维下标（yarn ramp 亦然），所以**旋转 Δ 对 yarn 也是精确的**；
  `mscale` 是幅度因子，纯旋转不能再乘。
- 量化 K 不能走图：`ggml_get_rows` 只出 F32，而 Vulkan 的 `supports_op`（`ggml-vulkan.cpp:9480`）
  只允许 `GET_ROWS/CPY/CONCAT` 向量化 src0，`SET_ROWS` 写 q8_0 不被支持 → 只能 CPU 逐 cell。

### 11.2 坑 19：K 存在 Walsh–Hadamard 基里（**本轮最贵的一个坑**）

这个 fork 默认对量化 K 启用 attention rotation（`llama-kv-cache.cpp:325-352`：`model.attn_rot`
&& 量化 type_k && head%64==0 → 本模型 `n_rot_k = 128`）。写 K 时 `llama_mul_mat_hadamard`
把 K 乘上正交 Hadamard 矩阵 H（Q 同样处理，故内积不变）。

**RoPE 与 H 不对易**，所以 `build_graph_shift` 是 `H → rope → H`。直接在存储字节上做 rope
得到的是 `R·H·K`，而不是 `H·R·K` —— 表现为：块位置正确、也能被 mask 看到，但答案是
纯复读（"我的工号是多少？ 答：我的工号是多少？"）。

修法：`llama_kv_fwht()`（正交 Sylvester，`res²=I`，O(n log n)）包住 rope。
判别方法：`LLAMA_ATTN_ROT_DISABLE=1` 时旧块文件**直接加载失败**（状态文件里存了 `n_rot_k`，
`llama-kv-cache.cpp:2782` 校验不匹配）——这恰好证明块是在 H 基下保存的。

### 11.3 坑 20：加载顺序会互相覆盖

块文件都从 position 0 开始。`kv_unified=true` 下，对**已被别的序列占用的 position** 写入会
**复用同一个 cell**，于是"先 load 两块、再一起平移"会让第二块覆盖第一块。
必须**加载一块→立刻搬走→再加载下一块**。

### 11.4 实测

| 项 | 数值 |
|---|---|
| 隔离性（未移动序列逐字节比对） | **0 B / 100 次移动**（0.00%），3/3 答案不变 |
| 移动耗时 | 50 token 块 **42 ms**；86 cell 两块 **76 ms**（≈33 MiB/s，瓶颈是 Vulkan 每次 submit+fence，不是带宽） |
| 批量优化的收益 | 逐 cell 508 ms → 连续区段批量 115 ms → 单块单次 42 ms |
| 端到端 | 两块（86 cell）attached，3 问全对，prompt 里 0 字符记忆文本 |

### 11.6 遗留

- yarn + `rope_freqs`（自定义 per-dim 因子）时返回 0，调用方应退回 `seq_add`；本模型不触发。
- M-RoPE（`n_pos_per_embd() != 1`）不支持；iSWA/MSA/DSV4 缓存走基类默认（返回 0）。
- 每次移动仍要 28 层 × 2 次传输；要进一步降到 ~5 ms 需要在 Vulkan 后端加"原地旋转行"算子（本轮明确不做）。
