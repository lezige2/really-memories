# 40k 原始流 · 记忆压缩/保留压测（A 方案，提交 B + C）

> 用户要求：不要只测 20 块；用 40k 原始数据流测“存取保留率（recall@k + 答案保留率）”，防截断、Lost-in-the-Middle、K2 长上下文雪崩、Verifier 承压。

## 0 先纠正一个架构事实（必须写进报告）

本系统**不会把 40k 原始流塞进 32k 上下文**：40k 原始流 → 记忆库（块）→ 查询时只挂 topk 4–6 块（约 800–1200 token）。
所以：
- 不存在“40k prompt 被 32k 截断”；
- 真正的截断点是 `LIBRARY_MAX=200` 与 `_fit_budget`（7680 token）；
- “压缩率”= 40k 原始 token / 实际挂载 token（~1k），压缩比 ~40:1；
- “保留率”= 目标事实是否仍可被检索并正确回答。

## 1 数据集（40k 原始流 → 200 块）

- **200 条记忆块**，每条 ~200 token 的“原始对话片段”（含上下文废话），总 ~40k token。
- 构成：
  - 120 条唯一事实（10 族 ×12；值只差末位，制造同族高相似）；
  - 40 条冲突链块（**10 条链 × A→B→C→D 4 次更新**，分散在 10%/40%/70%/90% 位置）；
  - 40 条噪声/闲聊（20% 干扰）；
- **深埋关键事实**：银行卡、核心会议、车牌等 10 条，分别放在库的 10%、50%、90% 位置；
- **多线程更新**：同一时间段内车牌、公司、出差地各更新一次，测试时间线。

## 2 查询（100 条）

- 直接问 40 条、同义/口语改写 30 条、冲突链“最后值”20 条、负例（问旧值/不存在）10 条；
- 查询不得与块共享车牌/号码等稀有 token（防字符串匹配假阳性）；
- 期望：目标块 id、期望值、不得出现旧值。

## 3 指标

| 指标 | 定义 | 门槛 |
|---|---|---|
| recall@4/6 | 目标块是否进挂载集 | 相对 20 块基线退化 ≤5pp |
| 答案正确率 | 值正确且不含旧值 | 同上 |
| 存取比 | 40k / 挂载 token | 报告值（~40:1，不称压缩率） |
| 截断损失 | `_fit_budget` 丢弃的目标块数 | 0 |
| K2 雪崩 | K2 生效/回退比、错隐藏 | 错隐藏 0 |
| Verifier | 错答被抓住的比例 | 报告，不设门槛 |
| 延迟 | P50/P95 | ≤ 2× 20 块基线 |

## 4 执行顺序（省窗口）

1. 生成 200 块 + 100 查询（CPU，先做）；
2. 建 20/50/100/200 四个子库（200 块全建一次，子库只切 DB 行；块文件共用）；
3. 先跑 **topk4 / K2-off** 20/50/100，定退化斜率；**200 先不建**，拐点未饱和再补；
4. 100 档再开 K2-on，测错隐藏/回退；
5. 全程独立 `kvmem/scale40k/`，不碰真实 `chat.db`；建库固定 seed、可重复。
6. **LiM 不混进本报告**：另做 K3′ 两组——a) 6 块全相关、位置 1/3/6 置换（30 条×3）；b) 候选 >7680 token 的预算截断（需 800+ token 长块）。本 40k 报告只写“库存取保留率”。
7. **冲突链必测反序**：造“同秒写入、id 与 created_at 反序”用例，K2 必须仍取 created_at 最新；归档块不得回答幽灵值。

## 5 风险

- 建 200 块耗时/显存：本地 GPU，预计 10–30 分钟；需暂停 8765 服务（同一张 10G 卡）。
- 200 token/块 ×6 挂载 =1200 token <7680，不会触发预算截断；若要测截断，需单独把预算调小（另开实验）。
- 合成数据自欺：查询改写、30% 噪声、10 族高相似、人工抽检 20 块。
