# llama-mem 项目流程（2026-11-04）

> 目的：先定流程，再写码。所有指标绑 HEAD sha；所有默认变更需用户点头。

## A. 产品数据流

```
写入
  用户输入
    → source_hash 精确判重（norm_hash 可选，默认 off）
    → 时间词解析（event_date 可选，默认 off）
    → 审计日志 write_trace
    → 备份/回滚点（写前）
    → SQLite memory_source + KV block（200 上限）
    → 写后一致性检查（块重叠/重复提示，不自动合并）

读取/回答
  query
    → 粗排 raw topN
    → **coverage 闸（粗排后、挂载前；当前 0.30）**
    → 挂载块（K2 off；若开只在池内）
    → 14B 生成
    → verifier v1（v2.2 显式）
    → **答案-问题对齐（槽位/主体；生成后、返回前，只判一次）**
    → 通过：答案；不通过：拒答/回模板，**不重新生成**
    → 审计日志 answer_trace
    → 文本 / TTS / CLI

追问/确认
  → 判不了/冲突：needs_confirmation 或追问
  → 超时/重启：不写、不覆盖（fail-closed）

归档
  → scan（超期+superseded/无引用；默认 dry-run）
  → archive zip + manifest + sha + 月份索引
  → fallback（去年/上月→unlocated+倒序盲搜）
  → reheat plan（superseded_by；只写副本）
  → 每步有备份/恢复命令，演练过
```

### 审计/日志层（每步可追溯）
- `trace_id`、query 摘要、候选数、闸原因、挂载 block_ids、verifier 结果、对齐结果、拒答原因、模型/latency；
- 不记录原始记忆全文；只记 id/哈希/原因；
- 用户可查“为什么拒/为什么挂这条”。

### 回滚点
- 写前/迁移前/归档前：备份文件 + sha + 恢复命令；
- 每个变更必须演练一次回滚；
- 回滚证据分“内容等价”和“字节等价”，不混写。

## B. 研发流程

```
问题定义
  → B 反预案（先找致命漏洞）
  → 预注册（过门实验：数据/门/回滚；spike：一页纸/2h/不作能力声明）
  → 隔离副本（不写 daily）
  → C 实现；C2 独立数据/评测；A 不参与标注
  → 逐 case 结果 + 误拒/误合并/回归
  → A/B 决策：默认开 / 保持 off / 封存
  → 小步 commit + 交接
```

硬规则：
- 所有指标必须绑 **HEAD sha**；跨版本比数作废；
- 失败项进**失效清单**（FAIL/边界/封存），一处登记，不重开；
- 判据只能由**用户**改；A/B 只能提议；
- 新能力默认 off 的准确口径：
  - 引入模型判断、或改变写入/检索语义 → **默认 off**；
  - 确定性、零模型、窄触发（如 meta 计数）→ 过门后可默认 on；
- 不用“已知缺陷”放行；每项单独过门，不四个一起上。

## C. 角色
- A：方案/优先级/整合；
- B：红队，能否决；
- C：实现；
- C2：独立数据/评测，不实现；
- D：文档/监控/交接；
- E：本地 commit，不 push；
- 用户：产品决策/判据变更/默认开关。

## D. 阶段
1. **P0 正确性**：判重、时间锚点、答案-问题对齐；
2. **P1 容量/归档**：归档、回热、主池控制；
3. **P2 检索**：先基线，再粗排/池内排序；
4. **P3 assistant/输出**：承诺记忆、TTS、CLI。
