# 关系判定：14B 优先 vs 1.5B · A 修订提案（提交 B）

> 用户追问："为什么不直接搞 14B？对话 9–10 token/s 就够了。"
> A 接受该质疑：1.5B 的唯一理由是"怕再占 9 GB"，但**复用同一个 14B 顺序调用不占额外显存**；写入是低频事件，多 1–2 秒可接受。故修订为 **14B prompt 先试，14B LoRA 兜底，1.5B 暂缓**。

## 1 修订后的三条臂（同一 60 条金标）

| 臂 | 做法 | 成本 | 备注 |
|---|---|---|---|
| R 规则 | 同主体+同谓词+不同值→correct；同族不同主体→new_subject；判不了→ambiguous | 0 | 现有 `_FB_RULES`/facet/attr 可复用 |
| Q 一律追问 | 全部 ambiguous，直接问用户"这是纠正还是新增？" | 0 | 准确率 100%，UX 成本待估 |
| P 14B prompt | 现模型 + 严格 JSON schema，temp=0，≤20 token | ~1–2 s/次 | 不训练、不新增模型 |

## 2 判定

- 若 P 过门槛（accuracy ≥95%、灾难错 0/60、真歧义不判 correct、0.9 桶 ≥19/20）→ **不训练**，P 只用于规则判不了的边角；
- 若 P 不过 → 才考虑 **14B LoRA**（不是 1.5B），且必须先解决部署：
  - 10 GB 卡装不下两个 14B 实例；
  - 写入时重载 adapter（~30 s）不可接受；
  - A10 跑判断（真实记忆不能上远程）不可接受；
  - 把 LoRA 合并进产品模型 = 切默认/改回答模型，禁止。
  → 所以 14B LoRA 可能"训得出来、落不了地"；若如此，回到 Q（追问）或 1.5B 小模型。

## 3 与残差门的关系

- 残差门仍先跑：规则错且真值=correct 的条数 <12/60 → 连 P 都不必上线，直接 Q。
- 残差 ≥12 → 再比 P 与 Q；P 若只比 Q 多救几条但引入误判，仍选 Q。

## 4 请 B 重点反驳

1. P（14B prompt）是否只是 V2 的翻版——"模型提议、relation 不可校验"，换了个模型大小而已？
2. P 的置信度是否可信？生成式自报 confidence 在 0.9 桶是否又会"稳定地错"？
3. 若 P 过 60 条，是否足以外推到真实写入流？是否需要第二套 held-out（不同族/不同模板）？
4. 14B LoRA 的部署死结是否意味着"训练 14B"从一开始就不该做？还是可以用"离线批处理 + 重载"换吞吐？
5. 用户 9–10 token/s 的前提是否成立（写一次记忆 20 token ≈2 s，可接受；但若一次写入要判多条候选，是否线性叠加）？
6. 1.5B 是否应彻底删除，还是保留为"14B prompt 与 14B LoRA 都失败后的最后选项"？
