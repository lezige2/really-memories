# 大数据/40k 记忆规模测试（A 提案，提交 B）

> 用户指出：一直测的是小数据（20 块/42 条），没测大数据；现场 32k 上下文，应该测 ~40k 来保证记忆可靠性。
> 先对齐口径：**40k 指"记忆库总量"（token），不是单次 prompt**。当前 `n_ctx=32768`、记忆区预算 `7680`、同时挂载 `≤6` 块，40k 不可能全进上下文；可靠性只能由**检索命中 + 挂载选择**保证。

## 1 现状与硬约束

| 项 | 值 | 含义 |
|---|---|---|
| `n_ctx` | 32768 | 单次上下文上限 |
| 记忆区预算 | 7680 token | 每次最多挂 ~6 块 |
| `MAX_MEMORIES` | 6 | 同时挂载上限 |
| `LIBRARY_MAX` | 200 块 | topk 模式库容量上限 |
| 当前库 | 20 块（~500 token） | 只有小数据 |

- 200 块 × 200 token = **40k token 库**，正好可在 `LIBRARY_MAX` 内做 40k 测试；不需要改上限。
- 若要 >200 块，需改 `LIBRARY_MAX`/分页，属产品变更，本轮不做。

## 2 测试设计（合成数据，不碰真实记忆）

1. **库**：`kvmem/scale40k/` 独立目录/DB；200 条合成记忆，每条 ~200 token（长句/多属性），总 ~40k token；含：
   - 唯一事实 100 条（可问答）；
   - 同族冲突 40 条（旧/新值）；
   - 干扰/近似 60 条（同实体不同属性、同值不同主体）。
2. **查询**：100 条，每条有唯一目标块与期望值；`topk=4/6` 两档。
3. **指标**：
   - **检索 recall@4/6**：目标块是否进挂载集（核心）；
   - 答案正确率（含值/不含旧值）；
   - K2 on/off 的 recall 与错隐藏；
   - P50/P95 延迟、建库时间、DB/块体积、VRAM 峰值；
   - 库从 20→200 的退化曲线（20/50/100/200）。
4. **对照**：20 块小库同查询集；K2 off；固定 topk=4。
5. **判定**：recall@6 ≥95%、答案正确率 ≥90%、K2 错隐藏=0、P95 延迟 ≤ 当前 2 倍；任一不达标则记录为规模缺陷，不调参掩盖。

## 3 成本与风险

- 建 200 个 200-token 块：本地 GPU，预计 10–30 分钟；块文件 ~400 MB；DB ~200 行。
- 100 查询 × 2 档 × 2 臂 ≈ 400 次 ask，约 15–30 分钟。
- 不写真实 `chat.db`；独立目录；不切默认；K2 flag 可关。
- 风险：建块时间/显存；`LIBRARY_MAX` 200 是硬顶；200 token/块可能触发预算截断（6×200=1200 <7680，安全）。
